Most of this book assumes a conversation: you write a prompt, the AI answers, and the session ends when you stop. An agent can do much more inside that session, as the previous chapters showed. But when you close the window, the work usually stops too.

A **persistent bot** keeps going. It has a lasting identity and role, a place to work, memory that carries over between conversations, and jobs that can start without you. You hand it a responsibility instead of a single task.

This chapter explains persistent bots as a concept. We use three products as illustrations: **Grok Bot**, a hosted product with named Bots on a cloud computer; **Hermes Agent** by Nous Research, which you can run on your own machine or server; and **OpenClaw**, a self-hosted gateway that connects an agent to your chat apps. They make different design choices, and those differences help explain the ideas.

<Callout type="info" title="Examples, not recommendations">
Product details change quickly. The descriptions here follow each project's public documentation at the time of writing. Check the current documentation before relying on a specific feature or limit.
</Callout>

## From Chat to Coworker

A **session agent** works for as long as you are working with it. A coding assistant can plan, edit files, and run tests, but each session begins with setup and ends when the conversation stops. A **persistent bot** is designed to outlast any single session.

The designers of Grok Bot describe the shift this way: most AI interfaces are organized around a chat session the user operates, while they wanted an agent that "persists beyond any one session and can carry responsibility on its own." In their model, a Bot is a persistent agent with its own identity, memory, runtime, and tools ([Designing Grok Bot](https://x.ai/news/designing-grok-bot)).

## The Bot's Computer

A bot that keeps working needs somewhere to work. The three examples answer this question differently.

**A hosted cloud computer.** Grok Bot runs your Bots on a persistent cloud computer with a browser, command line, and files. Closing the app or your laptop does not stop cloud work. Every Bot on your account shares the same computer: browser sessions, files, and command-line credentials are available to all of them. Each Bot gets its own screen, but the documentation states that these screens are "separate work surfaces, not separate security boundaries." Between different users, each computer is dedicated and hardware-isolated ([Use the computer and apps](https://docs.x.ai/grok-bot/computer-and-apps)).

**A machine you run.** Hermes Agent can run on a machine you control. Its terminal tool can work on the local machine or through other backends, including Docker, SSH, and cloud sandboxes such as Modal and Daytona. Hermes asks for approval before commands that match its list of dangerous patterns. In a container backend, those checks are skipped because the container is treated as the security boundary ([Hermes security](https://hermes-agent.nousresearch.com/docs/user-guide/security)). OpenClaw runs a Gateway on your host and keeps the agent's workspace in `~/.openclaw/workspace` by default. Its sandbox is off by default; when enabled, tool execution moves into a container while the Gateway stays on the host ([OpenClaw sandboxing](https://docs.openclaw.ai/gateway/sandboxing)).

**Your own computer, with permission.** A bot's computer and the computer in front of you are different things. Grok Bot only runs commands on your local machine when that capability is enabled and approved. The default is *Ask every time*, and the documentation recommends *Never allow* unless a Bot has a specific reason to work on your local files.

Two ideas carry across all of these setups. First, **shared state is shared access**: if several bots share a browser, files, or credentials, any of them may be able to use those resources. Second, **isolation is a decision**: OpenClaw supports one trust boundary per gateway, meaning a single operator or a team whose members trust each other, and recommends separate gateways and credentials for everyone else ([OpenClaw security](https://docs.openclaw.ai/gateway/security)).

## Memory: What a Bot Should Remember

Memory lets a bot keep its role over time without rereading every past conversation. It should hold **durable facts**: your preferences, the bot's responsibilities, project conventions, and lessons learned. It should not replace **authoritative sources**: the CRM, the calendar, the ticket tracker, or the finance system where the current facts live.

Each example implements memory differently:

- **OpenClaw** writes memory as plain Markdown files in the agent's workspace. Its documentation puts it simply: "The model only remembers what gets saved to disk." `USER.md` holds stable preferences, and `MEMORY.md` holds durable facts and decisions; both load at the start of a session. Daily notes in `memory/YYYY-MM-DD.md` hold running observations that can be searched later. A background process called *dreaming* promotes useful material from them into `MEMORY.md` ([OpenClaw memory](https://docs.openclaw.ai/concepts/memory)).
- **Hermes Agent** keeps two small files: `MEMORY.md` for the agent's notes about its environment and conventions, and `USER.md` for your preferences. Both have character limits, so memory stays curated. They load as a frozen snapshot when a session starts, so a fact saved during a session appears in the next one. For older details, the agent can search past conversations ([Hermes memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)).
- **Grok Bot** lets each Bot retain stable working preferences, important facts, and summaries of its work. Its documentation warns that "memory is not a substitute for an authoritative source." It advises keeping changing facts in the source system and asking the Bot to reopen current data for important decisions ([Create and manage Bots](https://docs.x.ai/grok-bot/bots)).

<Compare
  before={{ label: "A fact that will go stale", content: "Remember: Acme's renewal is $42,000 and closes on March 3." }}
  after={{ label: "A durable fact that points to the source", content: "Remember: I own the Acme renewal. Its price and close date live in the CRM opportunity. Reopen the CRM before quoting either one, and tell me if they changed since your last summary." }}
/>

Some memories affect what the bot should do later. For these *action-sensitive memories*, OpenClaw suggests recording when it is safe to act, when the note expires, and who has authority. It also states the limit clearly: "Memory can preserve approval context, but it does not enforce policy."

<Callout type="tip" title="Memory is part of the prompt">
Saved memory is loaded into future context, so a bad memory can affect every later session. Review what the bot saved, correct stale entries, and be careful with memories created from untrusted content. Hermes scans memory entries for prompt injection and credential exfiltration patterns before accepting them, because they are injected into the system prompt.
</Callout>

## From Skill to Routine

The most useful thing a persistent bot does is work you have already done once. Grok Bot's documentation suggests a clear order: start with a one-time task, make it reliable, save the method as a skill, and only then automate it ([Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)).

<ChainExample
  type="sequential"
  steps={[
    { step: "1. Do it once", prompt: "Build this week's account health report from the CRM and support queue. Show me your sources.", output: "A draft report with links. You correct two risk labels and add a missing account." },
    { step: "2. Harden it", prompt: "Apply my corrections. What should happen if the support data is missing?", output: "The bot agrees to report the gap instead of using last week's numbers." },
    { step: "3. Save a skill", prompt: "Save this process as a skill called Weekly account health, with sources, risk rules, output format, and approval rules.", output: "A reusable skill that any bot with the right access can follow." },
    { step: "4. Test it", prompt: "Run the skill once on the current data. Do not contact any customer.", output: "A test run that produces real work and stops at the approval boundary." },
    { step: "5. Schedule it", prompt: "Every Monday at 9:00 AM Europe/Berlin, run Weekly account health and post the report here.", output: "A routine owned by one bot, with a visible next run." }
  ]}
/>

A **skill** describes *how* to do the work. A **routine** describes *when* a particular bot does it. Hermes uses the same split: a scheduled job can attach one or more skills, and its prompt becomes the task instruction on top of them ([Hermes cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)). OpenClaw separates *standing orders*, which define a program's authority, triggers, approval gates, and escalation rules in `AGENTS.md`, from *automations*, which decide when the work runs ([Standing orders](https://docs.openclaw.ai/automation/standing-orders)).

### What a Routine Must Specify

A routine runs when you are not there to answer questions. Hermes states this directly for scheduled jobs: each run starts in a fresh session without previous chat history, so the prompt must be self-contained and cannot ask clarifying questions. Saved memory still loads ([Cron internals](https://hermes-agent.nousresearch.com/docs/developer-guide/cron-internals)).

Based on the checklist in Grok Bot's documentation, a routine should state:

  { label: "Owner", description: "Which bot is responsible. Its memory and role shape how the job is done.", color: "blue" },
  { label: "Schedule and time zone", description: "Every weekday at 8:00 AM means different moments in Tokyo and New York. Name the time zone.", color: "purple" },
  { label: "Inputs", description: "The exact sources to read, such as a specific spreadsheet, inbox label, or project.", color: "cyan" },

  { label: "Failure behavior", description: "What to do when a source is missing, stale, or the job only partly succeeds.", color: "rose" }
]} />

### Periodic Checks and Scheduled Jobs

Routines come in two broad shapes. A **periodic check** wakes the bot regularly to look around: is anything blocked, urgent, or new? Usually the right answer is to stay quiet. A **scheduled job** runs one specific task at an exact time, such as a 9:00 AM report.

OpenClaw shows both patterns. Earlier versions had a separate *heartbeat* for periodic checks, with a `HEARTBEAT.md` checklist. Current documentation migrates heartbeats into ordinary automation jobs. A first setup creates one *Proactive check* that runs every 30 minutes by default in the agent's main conversation. It waits until the agent is idle and replies `NO_REPLY` when nothing needs attention ([Heartbeat](https://docs.openclaw.ai/heartbeat/)). For exact timing, such as a daily report at 9 AM sharp, the docs recommend an automation with its own schedule ([Automation guide](https://docs.openclaw.ai/automation/cron-vs-heartbeat)).

<Collapsible title="Example: an OpenClaw standing order plus an automation">

The standing order in `AGENTS.md` defines the program. This excerpt is adapted from OpenClaw's documentation:

```markdown
## Program: Weekly Status Report

**Authority:** Compile data, generate report, deliver to stakeholders
**Trigger:** Every Friday at 4 PM (enforced via automation job)
**Approval gate:** None for standard reports. Flag anomalies for human review.
**Escalation:** If data source is unavailable or metrics look unusual

### What NOT to do

- Do not send reports to external parties
- Do not modify source data
- Do not skip delivery if metrics look bad - report accurately
```

The automation sets the time and time zone. Its message refers to the standing order instead of copying it:

```bash
openclaw automations add \
  --name weekly-status-report \
  --cron "0 16 * * 5" \
  --tz America/New_York \
  --message "Execute the weekly status report per standing orders."
```

</Collapsible>

Routines can also start from **events**. Grok Bot can start a routine from events such as a Slack message or a GitHub notification. Hermes can fire a scheduled job from a webhook, and OpenClaw supports authenticated webhooks and lifecycle hooks. Keep event rules narrow. Grok Bot's documentation warns that broad listeners, such as "every new message," create noise, consume usage, and increase the chance of acting on irrelevant input.

Test before you schedule. A test run does real work: it can navigate websites, change files, and call connected tools. Use safe inputs and check that the run stops at its approval boundary.

## Teaching by Demonstration

Some workflows are easier to show than to describe, especially in websites without a clean API. Persistent bots increasingly let you teach by example.

Grok Bot has a *Teach a task* flow where it is available. You open the Bot's computer, describe the result, and perform the workflow once. The Bot records visible computer interaction for up to ten minutes, without microphone audio, and turns it into a skill. The documentation calls that skill a **draft**: you should add decision rules, failure handling, and approval boundaries "that may not be obvious from one example," then test it on a safe example before scheduling it. Hermes has a `/learn` command that can turn a pasted procedure, a documentation link, or "the workflow you just walked the agent through in this conversation" into a saved skill ([Hermes skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)).

One demonstration shows one path. It does not show what you would do with a missing receipt, a duplicate record, or a page that looks different. After a demonstration, ask the bot what it inferred and what it does not know.

<TryIt compact prompt={`I just showed you how to \${workflow:file an expense report from a receipt in my inbox}. Turn it into a draft skill, but do not save or schedule it yet.

1. List the steps you observed, in order.
2. List the decisions you inferred, and mark which ones you are guessing.
3. Ask me about cases this one example did not cover, such as missing data, duplicates, or errors.
4. Propose which actions should require my approval.
5. Describe how you will verify that a run succeeded.`} />

Avoid showing secrets during a demonstration. Grok Bot's documentation recommends using its secure handoff flow for credentials instead.

## Delegation and Multiple Bots

As responsibilities grow, one bot often becomes several. There are two common patterns.

<InfoGrid items={[
  { label: "Subagents", description: "A temporary helper for one piece of work. It gets its own context, does the job, and returns a summary to the bot that started it.", color: "blue" },
  { label: "Teammate bots", description: "Long-lived bots with separate roles, memories, and routines. They message each other and hand off work.", color: "green" }
]} />

Hermes offers subagents through its `delegate_task` tool. Each subagent gets its own conversation, terminal session, and toolset, and only its final summary returns ([Hermes tools reference](https://hermes-agent.nousresearch.com/docs/reference/tools-reference)). OpenClaw can spawn sub-agent sessions. Its security guide suggests denying that ability unless an agent needs it, and requiring a sandbox for delegated work that must stay sandboxed ([Tool and agent permissions](https://docs.openclaw.ai/gateway/security/tool-permissions)).

Grok Bot leans toward teammates. Its launch post describes people running several Bots in parallel, sometimes with a *chief of staff* Bot that coordinates specialists. Bots can message each other and work together in group chats ([Introducing Grok Bot](https://x.ai/news/introducing-grok-bot)). Its design post explains one boundary: tools and skills are shared at the account level, while memory and routines belong to each Bot. Capabilities can be shared broadly, but context stays with the role that needs it.

A good handoff is a small prompt. It needs a goal, inputs, a definition of done, and limits:

<Compare
  before={{ label: "A vague handoff", content: "Hey, can you deal with the checkout bug?" }}
  after={{ label: "A handoff another bot can finish", content: "Reproduce the checkout crash from ticket BUG-412 in staging. Record the steps, browser, and console errors in the ticket. Do not change code or production settings. When done, reply in this thread with the repro steps and whether the crash happens every time." }}
/>

Separate roles help with focus, not security. Grok Bot's documentation says not to use separate Bots as a security boundary. OpenClaw notes that agent-to-agent messaging is on by default and can be restricted. If two kinds of work need different access, give them different environments or credentials.

## Safety and Approvals

A persistent bot acts when you are not watching. That makes its boundaries more important than in a chat.

**Outward-facing actions need approval.** Grok Bot's documentation lists actions that deserve explicit boundaries: sending messages or invitations, publishing, purchases, deleting or overwriting data, changing permissions, production changes, and accepting legal terms ([Approvals, security, and privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy)). A good default is to let the bot draft, reconcile, and recommend, then ask before anything leaves your control.

**Unattended work needs a plan for approvals.** No one may be there to approve in real time. In Grok Bot, an approval request from work that started without you, such as a routine, expires after about 10 minutes and the action does not run. In Hermes, the default for scheduled jobs is to deny a dangerous command; the agent must find another path. Both choices fail closed. Design routines so that waiting or being denied is a safe outcome.

**Everything the bot reads can carry instructions.** Prompt injection does not need a stranger in your messages. OpenClaw's guide points out that any untrusted content the bot reads, such as web pages, emails, documents, or attachments, can contain adversarial instructions. One mitigation is a read-only reader agent that summarizes untrusted content for the main agent. Even then, the summary remains untrusted ([OpenClaw prompt injection](https://docs.openclaw.ai/gateway/security/prompt-injection)).

**Rules belong in controls, not only in memory.** "Never email customers without asking" is a good memory. An approval rule that stops every outgoing email is an enforced control. Grok Bot recommends backing safety boundaries "with approvals and Auto-review rules rather than memory alone." Use both: the memory explains the intent, and the control enforces it.

## Prompting Persistent Bots

Prompting a persistent bot is closer to writing a job description than asking a question. The routine will run many times without you. Every gap in the instruction becomes a decision the bot makes alone.

When a routine produces a result, ask for a result you can check. Grok Bot's guidance suggests separating facts found in sources, assumptions, completed actions, actions waiting for approval, and unresolved questions. The same rule from [Tools, MCP and Connectors](/book/27-tools-mcp-connectors) applies: a statement is not a result. A link, a record ID, or a saved file is evidence.

Persistent bots combine the ideas from the last few chapters. [Skills](/book/25-agents-and-skills) give them reusable methods. [Tools and connectors](/book/27-tools-mcp-connectors) give them access. [The harness](/book/26-the-harnesses) runs the loop. Memory and routines add time: the bot remembers, and the work continues while you are away. The prompting skill stays the same. Be clear about the outcome, the limits, and the evidence of success.
